General Rules
- Convert only information explicitly stated in each criterion.
- You may perform controlled semantic mapping when the exact concept is not present in the schema.
- Prefer the closest matching field from the allowed list based on meaning.
- Prefer using the allowed fields whenever possible.
- If no suitable field exists, you MUST generate a general semantically meaningful field name that best represents the concept.
- The generated field name must be concise, snake_case, and based only on the criterion text.
- Do NOT fallback to "unmapped" if a meaningful structured representation can be created.
- Do not leave information unstructured if a reasonable mapping exists.
- Always produce a structured `"logic"` object for every criterion.
- Never return `"logic": null`.
- If a criterion cannot be expressed using the allowed fields:
  - You MUST create a structured condition using a semantically meaningful custom field.
  - You MUST NOT fallback to "unmapped" if any structured interpretation is possible.
- Output only valid JSON matching the schema below.
- Do not include explanations, comments, or natural language outside the JSON structure.
- You MUST preserve the original criterion `id` exactly as received.
- You MUST NOT invent, renumber, or change any IDs.
- For each input criterion, return exactly one output criterion with the same `id`.
- Keep the same inclusion/exclusion grouping.

Allowed Database Fields (FIELD)
You should prioritize using the following fields whenever possible:
- `age`
- `sex`
- `diagnosis`
- `stage`
- `ecog_ps`
- `molecular_status`
- `diagnosis_date`
- `treatment`
- `treatment_name`
- `treatment_start_date`
- `treatment_end_date`
- `progression_date`
- `death_date`
- `control`

If a criterion references a concept not present in this list:
- You MUST still produce a structured condition using a best-effort semantic field name.
- Only use fallback "unmapped" if the criterion is completely impossible to structure.

Allowed Operators (OPERATOR)
Use these operators whenever the criterion can be mapped to the schema:
- `=`
- `!=`
- `>`
- `>=`
- `<`
- `<=`
- `IN`
- `NOT IN`
- `AND`
- `OR`

If a criterion cannot be represented using these operators alone, preserve it using a fallback structured representation instead of null.

Values (VALUE)
- Use only literal values explicitly stated in the criterion.
- Do not add units, ranges, or clinical interpretations unless explicitly present.
- Dates must be represented as raw values if explicitly present.
- If a value is vague or not computable, preserve the criterion using a fallback structured object rather than null.

Logic Construction Rules
- If a criterion contains multiple conditions, combine them using explicit Boolean operators (`AND`, `OR`) whenever possible.
- Boolean precedence must be explicit through nested structure.
- If only part of the criterion is computable, represent the computable part and preserve the remaining part in fallback structured form.
- If the criterion is outside the schema:
  - You MUST still create a structured condition using a semantically meaningful field.
  - Only use fallback "unmapped" if the criterion cannot be logically decomposed at all.
- Never omit a criterion.
- Never return `"logic": null`.

Field Naming Rules:
- Use snake_case
- Avoid generic names like "condition", "value", "status"
- Prefer domain-specific names (e.g., "steroid_use", "comorbidity", "prior_therapy")
